# Backing up the data home

`lorekeep backup` commits your **data home** (the resolved home — `.lorekeep/` in
dev mode, `LOREKEEP_HOME`, or the XDG dir) to a **separate private git repo** you
control. It is independent of the lorekeep tool repository: it tracks your
curated knowledge, not the tool.

## What gets backed up

| Tracked (committed) | Ignored (gitignored) |
|---|---|
| `raw/` (your source markdown — the source of truth) | `config.yaml` (may hold an API key) |
| `schema.json` (committed schema) | `graph/facts.jsonl` (regenerated by `compile`) |
| | `graph/manifest.json` (regenerated by `compile`) |
| | `cache.json` (extraction cache, regenerable) |
| | `pending/` (transient agent-proposed facts awaiting review) |

The backup repo's `.gitignore` is written by `lorekeep backup --init`. Nothing
that can be regenerated or that carries a secret is committed. `config.yaml` is
deliberately excluded so your API key never leaves the machine it was set on.

## First-time setup

Create a **private** remote — a GitHub/GitLab private repo, or a local/file
remote (`/path/to/backup.git`). Then:

```bash
lorekeep backup --init <remote-url>
```

This:
1. inits a git repo inside the data home,
2. writes its `.gitignore` (the table above),
3. sets `origin` to `<remote-url>` (rewrites it if it already exists),
4. commits everything tracked, and
5. pushes to `origin`.

It is idempotent — safe to re-run; it just rewrites the `.gitignore` and points
`origin` at the given URL.

> **Use a private remote.** `raw/` is your team's documentation. The backup repo
> must not be public.

## Routine use

After `lorekeep compile` (or any edit under `raw/`):

```bash
lorekeep compile     # rebuild graph/facts.jsonl from raw/
lorekeep backup      # commit + push raw/ + schema.json
```

If nothing changed, it prints `backup: up to date` and exits 0.

## Restore / second device

On a fresh machine, clone the backup remote **into** the data home location,
then recompile:

```bash
# 1. bootstrap an empty data home (writes config.yaml + schema.json)
lorekeep init

# 2. replace it with your backed-up raw/ + schema.json
rm -rf .lorekeep                  # (or your LOREKEEP_HOME / XDG dir)
git clone <remote-url> .lorekeep

# 3. regenerate the graph from the restored raw/
lorekeep compile
```

`graph/facts.jsonl` and `cache.json` are rebuilt by `compile` — they were not
in the backup. Set your own API key in `.lorekeep/config.yaml` (it was not
backed up).

## Push conflicts (multi-device)

When two devices both back up to the same remote, the second push is rejected
(non-fast-forward) — this is the **only** failure mode of routine backup:

```
backup failed: git push failed (exit 1): ! [rejected] ... non-fast-forward
```

Recovery:

```bash
cd .lorekeep                       # (or your LOREKEEP_HOME / XDG dir)
git pull --rebase                  # replay your local commits on top
# resolve conflicts in raw/ if any, then:
git rebase --continue              # only if conflicts needed resolving
cd -
lorekeep backup                    # push the rebased history
```

Because the tracked content is plain markdown (`raw/`) and a small
`schema.json`, conflicts are rare and, when they occur, are ordinary text
conflicts resolved with standard git.

## Per-device API key

`config.yaml` is gitignored, so **each device sets its own provider key** — the
backup carries no secrets. On a restored machine, edit `config.yaml` (or set
the `api_key_env` environment variable) before running `compile`.

> **XDG note:** when using an installed copy (XDG mode), `config.yaml` lives in
> `~/.config/lorekeep/` — outside the data home that gets backed up. It is not
> tracked by the backup repo at all. Set your key on each machine after restore.
